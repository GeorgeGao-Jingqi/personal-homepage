我越来越觉得，图表只是分析工作的一个界面，而不是工作的终点。

一个完整的分析过程至少要回答三件事：

1. 业务真正想知道什么？
2. 数据能支持什么程度的判断？
3. 判断之后，谁可以采取什么行动？

如果只把分析交付成一张看起来漂亮的图，读者仍然需要自己完成问题定义、口径确认和行动设计。这样做的成本只是从分析师转移到了团队。

## 我现在使用的检查顺序

| 层次 | 要确认的问题 |
| --- | --- |
| 问题 | 这个问题是否对应真实决策？ |
| 证据 | 数据的时间范围、口径和缺失情况是什么？ |
| 解释 | 观察到的变化有哪些可能原因？ |
| 行动 | 下一步要验证或改变什么？ |

所以我会把图表放在中间，而不是放在开头。先让问题变得具体，再决定什么图最能减少误解。

这也解释了我为什么喜欢把项目写成“问题 / 方法 / 影响”：它强迫我说明分析结果如何进入真实工作流。
